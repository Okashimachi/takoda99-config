# takoda99-config 仕様書

> Takoda99（たこ焼き経営バトルロイヤル）の **運営用 管理UI**。
> ゲームサーバー `Takoda99-Server` の `/api/params`・`/api/words` を叩く薄いフロント（Next.js / Vercel）。
> 前作 Textro99 の `config-front` を土台にするが、**パラメータ構造が入れ子になった**ことと
> **お題（words）編集が加わった**ことで作り直しが必要。

- 数値の正典: `Takoda99-Server/internal/game/params.go`（本リポの型は**手動ミラー**）
- API 契約の正典: `Takoda99-Server/internal/configapi/`（`handler.go` = params / `words.go` = お題）
- 仕様の背景: `Takoda99-Docs/02_共通仕様/03_パラメータ仕様.md`

---

## 1. 目的

イベント当日に**ビルドもデプロイもせず**にゲームバランスとお題を変えられるようにする。想定利用者は
運営（りーせ＋当日オペ）で、エンジニアでなくても値の意味が分かる UI にする。

達成したいこと:

1. 人が集まらない → `matching.minPlayers` を下げて即座に試合を回す（**最優先**）
2. 試合が長い / 決着しない → `storm`・`heat` を締める
3. Bot が強すぎ / 弱すぎ → `bot` を触る
4. お題が繰り返しでダレる / 誤字がある → words を足す・直す

## 2. 非目標（やらないこと）

- ユーザー管理・ロール分け（共有トークン1本で足りる）
- 監査ログのサーバー保存（履歴は端末 localStorage のみ）
- 進行中の試合へのライブ介入（反映は §7 のタイミングに従う）
- 試合結果の閲覧・集計ダッシュボード（`results` テーブルは別課題）
- BFF 化によるトークン秘匿（将来課題 §12）

## 3. サーバー側の現状（この仕様の前提）

実装済み。**フロント側からサーバーを変更する必要は原則ない**（例外は §6.4・§12）。

### 3.1 `GET /api/params`
- 認証**不要**。`game.GameParameters` の完全な JSON を返す。
- DB 未設定時 `503`。
- サーバー内部で **2秒キャッシュ**（`db.ConfigStore` の `cacheTTL`）。保存直後の再取得は最大2秒遅れる。

### 3.2 `POST /api/params`
- `X-Admin-Token` 必須（定数時間比較）。ボディ上限 64KiB。
- サーバーが `GameParameters.Validate()`（§5.4）を通し、通れば JSONB 1行を上書き。
- レスポンス = 保存後の値（フロントはこれを「サーバー現在値」として採用する）。
- ステータス: `200` / `400` 検証失敗（本文に理由） / `401` トークン不一致 / `503` DB かトークン未設定。

### 3.3 `GET /api/words`
- 認証不要。クエリ `?category=&level=` でフィルタ（両方省略で全件）。
- 返り値 `WordEntry[]`: `{ id, text, reading, keystrokeCount, level, category }`。

### 3.4 `POST /api/words`
- `X-Admin-Token` 必須。ボディ上限 1MiB。
- ボディ `{ mode: "upsert" | "replace", words: WordEntry[] }`（`mode` 省略時 `upsert`）。
- `words` が空配列なら `400`。
- サーバー側の補完: `reading` 空 → `text` を使う / `keystrokeCount` が 0 → `reading` から算出 / `category` 空 → `"general"`。
- レスポンス = 保存後の**全件**。
- **`mode: "replace"` は `DELETE FROM words` してから挿入する**。送っていない語は消える。破壊的。

### 3.5 `DELETE /api/words/{id}`
- `X-Admin-Token` 必須。成功時 `204`。存在しない id は `500`（サーバーが error を返すため）。

### 3.6 CORS
- 許可オリジンはサーバーの環境変数 `CONFIG_FRONT_ORIGIN`（カンマ区切り）。未設定なら `*`。
- 許可ヘッダは `Content-Type, X-Admin-Token`。
- **Vercel にデプロイしたら、そのURLを `CONFIG_FRONT_ORIGIN` に入れる作業が必ず要る**（本番URL＋必要ならプレビューURL）。

## 5. パラメータ編集画面（`/`）

### 5.1 スキーマ表現 — Textro99 からの最大の変更点

Textro99 の `GameParameters` は `group.field` の **2階層フラット**で、`Record<string, number>` として
扱えた。Takoda99 は入れ子がある:

- `credit.leaveLoss.{normal,bonus,claimer,buzz}` — 3階層
- `customer.{normal,bonus,claimer,buzz}.{weight,patienceBaseMs,orderCount}` — 3階層
- `customer.{...}.attribute` — **数値ではなく文字列**（`"Normal"` / `"Bonus"` / `"Claimer"` / `"Buzz"`）

よって Textro99 の `lib/params.ts` の設計（グループ→フィールドの2重ループ）をそのまま流用できない。

**採用する方式（パス方式 + ツリー温存）**

1. 画面スキーマは**ドット区切りパスの平坦なリスト**で持つ。
   ```ts
   type FieldSpec = {
     path: string;      // 例 "customer.buzz.patienceBaseMs"
     label: string;
     unit?: string;
     float?: boolean;   // true=小数可（既定は整数）
     min?: number; max?: number;
     help: string;      // 必須。「どこに効くか／上げ下げの効果」
   };
   type GroupSpec = { key: string; title: string; desc: string; fields: FieldSpec[] };
   ```
2. 値の読み書きは `getPath(obj, path)` / `setPath(obj, path, v)` のヘルパ経由。
3. **編集対象の数値リーフだけをスキーマで宣言し、それ以外のフィールドは触らずに温存する。**
   保存時は「サーバーから取得した JSON をそのまま土台にして、編集した数値リーフだけを上書き」して
   POST する。これで
   - `customer.*.attribute`（文字列）が消えない ← **消すと客の属性が全部 Normal 相当になり壊れる**
   - サーバーが先に増やした未知フィールドも保存で消えない

   ※ Textro99 の `mergeWithDefaults` は「未知フィールドを温存しつつ既知の欠損を埋める」だったが、
   数値前提だったので**そのままでは使えない**。パス方式で書き直す。
4. 取得値に既知パスが欠けている（＝古いサーバー）場合のみ、内蔵デフォルトで補完する。

### 5.2 編集項目（全56項目）

`params.go` の 12 グループ。表示順もこの順とする。**help（各項目の説明文）は必須**で、
「何の値か」＋「上げるとどうなるか」を書く。以下は help の骨子。

#### `matching` — マッチング（当日いちばん触る）
| パス | ラベル | 既定 | 説明の骨子 |
|---|---|---|---|
| `matching.minPlayers` | 開始最小人数 | 20 | カウントダウン開始に必要な人数。**当日ここを下げて試合を回す**。 |
| `matching.maxPlayers` | 最大人数 | 99 | 到達で即開始。 |
| `matching.startCountdownMs` | 開始カウントダウン | 15000 | 最小人数到達から開始までの秒数。 |
| `matching.minFill` | Bot補完人数 | 99 | この人数まで Bot で埋める。0＝補完なし。 |

> ⚠ サーバーを `--bots N` 付きで起動していると `minFill` はその N で**上書きされる**
> （`cmd/server/main.go` の `botsExplicit`）。UI に注意書きを出す。

#### `session` — 内部周期（基本さわらない）
`session.tickIntervalMs`(150) / `session.publishIntervalMs`(250)。小さいほど滑らかで CPU・帯域を食う。

#### `credit` — 信用（ライフ）
`credit.initialLife`(3) と `credit.leaveLoss.{normal,bonus,claimer,buzz}`(1/1/1/2)。
**客に帰られた時だけ**減り、0 で自滅脱落。バズ客に帰られると重い（2）のが既定。

#### `customer` — 客
`customer.total`(300) ＋ 属性4種 × 3項目。
- `weight` — 出現比（合計に対する相対値。70/15/10/5）
- `patienceBaseMs` — 来店時の我慢時間の最大値
- `orderCount` — 1人が出す注文数（お題数）

| 属性 | weight | patienceBaseMs | orderCount |
|---|---|---|---|
| normal | 70 | 8000 | 2 |
| bonus | 15 | 9000 | 2 |
| claimer | 10 | 6000 | 1 |
| buzz | 5 | 12000 | 4 |

#### `eval` — 評価
`emaAlpha`(0.3) / `weightAccuracy`(0.5) / `weightSpeed`(0.5) / `speedBaselineMs`(4000) /
`speedCap`(2.0) / `minMsPerWord`(200) / `buzzBonus`(0.2) / `buzzDecay`(0.98) / `buzzCap`(0.5)。

実装準拠の要点（`internal/game/session.go`）:
- 速度成分 = `clamp(speedBaselineMs / 実所要ms, 0, speedCap)`。基準より速いほど1超え。
- `minMsPerWord * orderCount` が所要時間の**下限**（不正・オートクリック対策）。
- バズ加点は `clamp(現在値 + buzzBonus, 0, buzzCap)`、毎tick `buzzDecay` 倍で減衰。

#### `phase` — フェーズ移行（Early→Mid→Late）
`midAliveThreshold`(70) / `lateAliveThreshold`(30) / `midTimeMs`(30000) / `lateTimeMs`(90000)。
**生存数と経過時間のどちらか先に到達で移行**。

#### `heat` — 火力（お題難度）
`base`(0) / `perAliveDrop`(0.1) / `phaseEarly`(0) / `phaseMid`(3) / `phaseLate`(8) / `maxLevel`(20)。
実装式: `heat = base + floor(perAliveDrop × (総店数 − 生存数)) + フェーズ加算`、上限 `maxLevel`。

> ⚠ **お題（words）の level は既定で 0〜4 しかない**。`heat` が 5 以上になっても、その level に語が
> なければ下位 level にフォールバックする（`odai.ConfigurablePool.Next`）。`maxLevel` を上げるなら
> words 側にも該当 level の語を入れること。UI で警告する（§5.5）。

#### `storm` — 下位淘汰
`intervalTicks`(40) / `warnTicks`(10) / `thresholdPct`(0.10)。
`intervalTicks` ごとに正規化評価の下位 `thresholdPct` を強制脱落、`warnTicks` 前に予告配信。

> ⚠ **Takoda99 に試合の制限時間は存在しない**（proto v0.3.0 で `matchTimeLimitMs` を削除）。
> 終了条件は「生存店＝1」のみで、**決着を保証しているのは storm だけ**。
> `intervalTicks = 0` は淘汰無効＝**試合が終わらなくなる**。サーバーの `Validate()` は 0 を通すので、
> フロント側で強い警告を出す（§5.5）。

#### `distribution` — 客の分配
`queueRefillThreshold`(3) / `weightFloor`(0.25)。
実装式: 行列が `queueRefillThreshold` 未満の店だけが分配候補。重み = `(weightFloor + 正規化評価) ÷ (行列長 + 1)`。
`weightFloor` は評価0の店にも客が来る下駄。下げるほど「評価が高い店に客が集中」する。

#### `patience` — 我慢ゲージ
`lateMul`(0.6) / `alertMs`(2000)。
実装式: 終盤フェーズでは経過時間を `dt ÷ lateMul` として扱う（0.6 なら約1.67倍速で減る）。
**下げるほど終盤がキツくなる**（名前から受ける印象と逆なので help で明示する）。
`alertMs` は残りこの時間で離脱アラートを出す。

#### `presentation` — 演出しきい値（ゲーム進行に影響しない）
`finalStageAliveThreshold`(20) / `finalRushAliveThreshold`(10)。クライアントの見た目切替のみ。

#### `bot` — CPU の強さ
`baseAccuracy`(0.85) / `baseElapsedMs`(3000) / `accuracyJitter`(0.1) / `elapsedJitterMs`(500)。
`baseElapsedMs` が1お題にかける時間（小さいほど強い）、`baseAccuracy` が精度（0〜1）。

### 5.3 差分・未保存表示

Textro99 の挙動を踏襲する。
- サーバー現在値と編集値のパス単位 diff を計算し、変更フィールドに `●`（琥珀色）を付ける。
- サイドパネルに「未保存の変更 N件」を `旧値 → 新値` のリストで表示。
- 「再読み込み」時に未保存があれば `confirm` で確認。
- 各入力の下に `既定 <値>` を常時表示。

### 5.4 検証（hard / 保存ボタンを無効化）

サーバー `GameParameters.Validate()` と**同じ条件**を必ず含める。サーバーで弾かれてから気づくのを防ぐ。

サーバー同等（必須）:
- `customer.total > 0`
- `credit.initialLife > 0`
- `session.tickIntervalMs > 0`
- `bot.baseElapsedMs > 0`
- `0 ≤ bot.baseAccuracy ≤ 1`
- `heat.maxLevel > 0`
- `storm.intervalTicks ≥ 0`
- `0 ≤ storm.thresholdPct ≤ 1`
- `phase.midAliveThreshold ≥ 0`

フロント追加（整合性）:
- 全項目が有限な数値（`NaN`・空欄・`Infinity` を弾く）／`float: false` の項目は整数
- 全項目が 0 以上
- `matching.minPlayers ≤ matching.maxPlayers`
- `phase.lateAliveThreshold ≤ phase.midAliveThreshold`（終盤の方が生存数は少ない）
- `phase.midTimeMs ≤ phase.lateTimeMs`
- `storm.warnTicks ≤ storm.intervalTicks`（予告が間隔より長いと出ない）
- `customer` の `weight` 合計 > 0
- `presentation.finalRushAliveThreshold ≤ presentation.finalStageAliveThreshold`
- `patience.lateMul > 0`（0 だと終盤の短縮処理が無効になる）

### 5.5 リスク警告（soft / 確認ダイアログ）

保存自体は可能だが事故りやすい値。保存前に `confirm` で列挙する。

- **`storm.intervalTicks === 0` または `storm.thresholdPct === 0`
  → 「下位淘汰が無効です。Takoda99 には制限時間がないため、試合が終わらなくなる可能性があります」**
- `matching.minPlayers < 3`
- `matching.minFill === 0` かつ `minPlayers` が大きい → 人力だけで埋める必要がある
- `heat.maxLevel > (words に存在する最大 level)` → 「level N の語がありません」
  （`GET /api/words` の結果から算出。取得できない場合は既定の 4 と比較）
- `customer.total < 生存想定店数 × queueRefillThreshold` → 客が枯れる
- `eval.weightAccuracy + eval.weightSpeed` が 1 から大きく離れている
- `bot.baseAccuracy > 0.95` または `bot.baseElapsedMs < 1000` → Bot が強すぎ
- `session.tickIntervalMs < 50` → CPU 負荷（本番は e2-micro 0.25vCPU）
- `patience.lateMul < 0.3` → 終盤が理不尽

### 5.6 プリセット・変更履歴

Textro99 と同じく **localStorage のみ**（端末ローカル、サーバー共有ではない）。
キーは `takoda99-*` に改名する（`t99-*` は Textro99 と衝突する）。

- `takoda99-admin-token` — 管理トークン
- `takoda99-presets` — 名前付きプリセット（保存/読込/削除）
- `takoda99-history` — 保存成功時のスナップショット、最大20件

推奨プリセット（初期同梱を検討）: `本番`（既定値）/ `少人数テスト`（`minPlayers: 2`, `minFill: 8`）/
`高速決着`（`storm.intervalTicks` を詰める）。

### 5.7 JSON プレビュー
右カラムに現在の編集ツリーを整形表示（Textro99 同様）。ハッカソン当日のデバッグで効く。

## 6. お題編集画面（`/words`）— 新規

### 6.1 一覧
- `GET /api/words` の全件をテーブル表示: `id / text / reading / keystrokeCount / level / category`
- フィルタ: level（0〜4＋その他）、category、テキスト部分一致（**部分一致は取得後のクライアント側で**。
  サーバーのクエリは完全一致のみ）
- level ごとの件数サマリを出す（`heat.maxLevel` との突き合わせに使う）

### 6.2 編集モデル — サーバー API の制約を吸収する

**words テーブルの一意キーは `(text, level)` で、`id` は upsert に使われない。**
つまり `POST` で既存行の `text` や `level` を変更することはできず、**別の行が増える**。
フロントはこれを隠蔽し、次の操作に落とす。

| ユーザー操作 | 実際のリクエスト |
|---|---|
| 語を新規追加 | `POST {mode:"upsert", words:[新語]}` |
| `reading` / `category` / `keystrokeCount` だけ変更 | `POST {mode:"upsert", words:[変更後]}`（`text`,`level` は据え置き） |
| `text` または `level` を変更 | `DELETE /api/words/{旧id}` → `POST {mode:"upsert", words:[変更後]}` の2段 |
| 語を削除 | `DELETE /api/words/{id}` |

- 変更は行ごとに即時送信せず、**編集をためて「保存」で一括送信**する（未保存バッジ付き）。
- 2段階になる操作は、途中で失敗した場合に**削除だけ通って追加が失敗する**ことがあり得る。
  失敗時は「元の語が消えた可能性があります」と明示し、再読み込みを促す。
- `keystrokeCount` は**空欄で送ればサーバーが `reading` から算出する**。既定は空欄運用とし、
  手で入れたい時だけ上書きできるようにする。

### 6.3 一括入力（CSV / TSV 貼り付け）
テキストエリアに `text,reading,level,category` の行を貼って一括追加できるようにする。
Excel / スプレッドシートからのコピペを想定（TSV も受ける）。

- パース結果をプレビュー表で見せてから送信
- `mode` は既定 **`upsert`**
- `mode: "replace"` は「**既存の全語を削除して置き換える**」と赤字で警告し、
  「REPLACE」と手入力させる二段確認を要求する

### 6.4 サーバー側の既知の穴（フロントでは埋められない）
- 存在しない id の `DELETE` が `404` ではなく `500` を返す。→ フロントは 500 でも
  「すでに削除済みかもしれません」と案内し、一覧を再取得する。
- 語の**更新用エンドポイント（PATCH）がない**。§6.2 の2段運用で回避する。
- 将来サーバー側に issue を立てる（§12）。

## 7. 反映タイミング（運営が知りたい一番のこと）

**Textro99 とは挙動が違う。UI に明記する。**

| 変更対象 | 反映 | 根拠 |
|---|---|---|
| `matching.*` | **数秒後（最大2秒＋マッチングループ周期）。再起動不要** | `matchmaking` の `GetParams` が毎ループ `provider.Load` を呼ぶ（`main.go:118`）。Textro99 は起動時スナップショットだったが、Takoda99 は動的リロード対応。 |
| それ以外の全パラメータ | **次の試合から** | `loadDeps()` が試合開始ごとに `provider.Load` する（`main.go:50`） |
| words | **次の試合から** | 同上（`wordStore.LoadAll` を試合開始ごとに実行） |
| 進行中の試合 | **変わらない** | `Session` は開始時の `Params` を保持 |

サーバー側 `ConfigStore` の 2秒キャッシュがあるため、保存直後に `GET` すると古い値が返ることがある。
保存レスポンス（保存後の値）をそのまま採用し、`GET` で確認し直さない。

## 8. 認証とセキュリティ

Textro99 の「案A」を踏襲する。

- 管理トークンは**ブラウザで実行時に入力**し、`X-Admin-Token` としてサーバーへ送る。
  ビルドに焼き込まない。任意で localStorage に記憶（`type="password"` の入力欄）。
- `GET` は認証不要（現在値の閲覧は公開）。
- サーバー側の `CONFIG_ADMIN_TOKEN` と `CONFIG_FRONT_ORIGIN` が設定されていることが前提。
  未設定なら `503` が返るので、その旨をそのまま UI に出す。
- **`https` 前提**。Vercel も `takoda99.mooo.com`（Caddy + Let's Encrypt）も TLS 済み。

## 9. 環境変数・技術スタック・デプロイ

| 変数 | 意味 |
|---|---|
| `NEXT_PUBLIC_GAME_SERVER_URL` | ゲームサーバーのベースURL。既定 `https://takoda99.mooo.com` |

- Next.js（App Router）+ TypeScript + Tailwind CSS。DB もサーバーサイド処理も持たない完全な静的フロント。
- CI: GitHub Actions で `npm ci && npm run build`（型チェック込み）。Textro99 と同じ。
- デプロイ: Vercel に本リポを Import → `NEXT_PUBLIC_GAME_SERVER_URL` を設定 → デプロイ
  → **払い出された URL をサーバーの `CONFIG_FRONT_ORIGIN` に追加**（この最後の手順を忘れると CORS で死ぬ）。

## 10. エラー表示

| 状況 | 表示 |
|---|---|
| `GET` 失敗（初回） | デフォルト値を表示し「サーバーに繋がらないためデフォルト表示」 |
| `GET` 失敗（2回目以降） | 前回値のまま「取得に失敗、前回値のまま」 |
| `401` | 「認証に失敗しました（トークンが違います）」 |
| `400` | 「サーバー検証エラー: 〈本文〉」をそのまま出す |
| `503` | 「サーバーの config 機能が無効です（`DATABASE_URL` / `CONFIG_ADMIN_TOKEN` 未設定）」 |
| CORS / ネットワーク | 「通信エラー」＋ `CONFIG_FRONT_ORIGIN` の設定を疑うよう案内 |

## 11. 受け入れ基準

1. `npm run build` が型エラーなしで通る
2. サーバーの `GET /api/params` の値が全56項目、正しいラベル・既定値付きで表示される
3. `customer.*.attribute` が保存後も文字列のまま保持されている（POST → GET で確認）
4. 検証エラーのある状態で保存ボタンが押せない
5. `storm.intervalTicks = 0` を保存しようとすると警告が出る
6. words の追加・reading修正・削除・text変更（2段）が一覧に正しく反映される
7. CSV 貼り付けで10語を一括追加できる
8. `matching` と他項目で反映タイミングの説明が UI 上に出ている
9. トークン未入力で保存を押すと、リクエストを投げる前に UI が止める
